# WSL Dotfiles — 前提知識（wsl-home 固有）

> 出所: ユーザー提供の引き継ぎ文書（2026-10-19）と、同日の参照リポジトリ確認に基づきます。
> 実環境の値は共有を受けた時点のものです。使う前に現在値の再確認を前提としてください。
> 判断ルール（守るべき規約）は `AGENTS.md §6` が正本です。本スキルは「事実と前提」を集める場所です。

## 鉄則

1. **AI 作業環境とユーザー実環境は別物です。** AI 作業環境のコマンド結果をユーザー PC の状態と混同しないでください。
2. **設計が先、実装が後です。** 合意前に、ユーザー実環境のインストール・ファイル移動・上書き・リンク作成を前提に進めないでください。自動コミット・自動プッシュ（dotfiles の運用として）も未合意です。
3. **秘密情報は扱わせない・置かない。** 秘密鍵・トークン・パスフレーズ・実メールアドレス・`.env` の内容をチャットで共有させず、本リポジトリ（公開）にも置きません。

## ユーザー実環境の概要（2026-10-18〜19 共有時点）

| 項目 | 共有された値 |
| :--- | :--- |
| OS / WSL | Windows 11 + WSL2、Ubuntu 24.04.5 LTS（noble）、systemd 有効 |
| ホーム / シェル | `/home/ubuntu`、zsh 5.9（ログインシェル設定済み）+ Oh My Zsh（`ZSH_THEME=""`）+ Starship |
| 作業場所 | `~/workspace/projects/`（通常）/ `sandbox/`（実験）/ `temp/`（一時）。基本は Linux 側 |
| パッケージ / バージョン管理 | 基本 `nala` を使用。言語ランタイムは `mise`（`~/.local/bin/mise`）で管理。Python 開発用は `uv`、システム Python は触らない |
| 主なツール | Node.js LTS（mise）/ pnpm（`$PNPM_HOME/bin/pnpm` が実体）/ Bun / Go（mise、`GOBIN=$HOME/.local/bin`）/ Rust（rustup）/ Git + SSH（keychain で agent 再利用）/ Docker Engine（WSL 内、Desktop ではない） |
| エディタ | VS Code 中心（WSL 内で `code .`、WSL 側 Git/SSH を使用） |
| 注意 | Windows 側 C ドライブの空きが厳しい（共有時点）。Docker イメージやビルド生成物の肥大に注意し、不要データの削除を勝手に行わない |

好み・運用方針（確定事項）:

- **Starship の現在の見た目は好みのため変更しません。**
- Oh My Zsh のプラグインは可能な限り `plugins=(...)` で管理したい希望があります（`zsh-completions` は初期化前に `fpath` へ入れる方針を案内済み。ただし導入後の最終 `.zshrc` は未取得です）。
- 一度に大きく変更せず、理由と影響を説明しながら結果を見て進めます。
- 現行 zsh 設定の要点（共有済み）: `PNPM_HOME` / Bun / `~/.local/bin` を PATH に追加し重複を抑制、mise は絶対パスで初期化、fzf（0.44.1）は `/usr/share/doc/fzf/examples/*.zsh` を読み込む方式、keychain による SSH agent 再利用、末尾で Starship と zoxide を初期化。これらを置き換える提案は、維持すべき前提として扱ってください。

## 合意済み: シンボリックリンクの方針

```text
~/.zshrc ──シンボリックリンク──▶ （リポジトリ内実体。例: dotfiles/zsh/.zshrc）
                                 実体・Git 管理対象は 1 つだけ
```

- 期待する動作: (1) `~/.zshrc` を編集するとリポジトリ側の実体が変わり Git 差分に現れる。(2) リポジトリで `git pull` すると `~/.zshrc` 経由でも更新が見える。相互リンクや常時同期プロセスは不要です。
- 限界: エディタやインストーラーが「リンク自体を通常ファイルに置き換える」保存をするとリンクが外れる場合があります。そのため、実際の VS Code での保存テストと、リンク状態の検査（リンク切れ・通常ファイル化・想定外リンク先・zsh 構文）を用意する方針です。
- リンクが壊れたときの復旧順序: 差分確認 → 必要な変更の回収 → バックアップ → リンク復元。一方を無断で上書きしません。
- ファイル更新は既存 zsh セッションを自動では再読込しません。新しいタブで反映確認します。pull 時の競合は通常の Git と同様に解決します。
- `~/.config` 全体はリンクせず、必要なファイル / 専用サブディレクトリを明示的にリンクする案が推奨されています（最終合意前）。`/etc` 配下は sudo 配置を通常手順に含めず、参考ファイルと手順として扱う案です。

## 参照リポジトリ UbuntuHome（構造と gg の参考）

zsh は「読み込み専任の `.zshrc` + 分割モジュール」構造です（2026-10-19 確認）。

| ファイル | 役割 |
| :--- | :--- |
| `.zshrc` | `~/.zsh/*.zsh` と `~/.zsh/functions/**/*.zsh` を順に読み込むだけ |
| `.zsh/00-env.zsh` | 環境変数・PATH・ロケール |
| `.zsh/10-omz.zsh` | Oh My Zsh・プラグイン。関数 `gg` と競合する OMZ エイリアスを `unalias gg` で解除 |
| `.zsh/20-aliases.zsh` | エイリアス・便利関数 |
| `.zsh/30-tools.zsh` | Bun / fzf / mise / zoxide / Starship の初期化 |
| `.zsh/functions/<名前>/<名前>.zsh` | 独自関数（`gg`、`uncd` など） |

`gg` は Zsh 関数で、依存は `git` / `gum` / `delta` / `fzf` です。設計時に特に注意すべき挙動は次のとおりです。

| コマンド | 実際の挙動（参照実装） |
| :--- | :--- |
| `gg push` | 単なる push ではない。**全変更を stage → commit → push** する |
| `gg set --auto-push true` | 上記を**確認なし**で実行し、メッセージは `Update` 固定。設定は `~/.config/gg/config`（または `GG_CONFIG`）に保存 |
| `gg undo` | `git reset --soft HEAD~1`（履歴の書き換え）。説明と確認が必要 |
| `gg sync` | `fetch --all --prune` → `pull --rebase` → `push` |
| `gg delete` / `gg clean` | 削除は安全な `-d` のみ（自動で `-D` にしない）/ clean はドライラン表示のみ |
| その他 | `clone`（SSH URL 化して確認後 clone）/ `status` / `diff`（ファイルを選んで差分表示）/ `log` / `remote` / `tag` / `add`（全 stage 後に差分確認）/ `commit` / `pull`（通常 pull）/ `switch`（fzf 選択）/ `new` / `fetch` / `stash` / `pop` |

## 参照先から無条件にコピーしない点

1. PATH を固定配列で置換しない（Windows 連携や VS Code CLI 等、既存 PATH を維持する必要がある）。
2. pnpm の PATH は実環境に合わせる（実体は `$PNPM_HOME/bin/pnpm`）。
3. `fzf --zsh` を無条件に使わない（実環境の fzf は 0.44.1 のため、従来の examples 読み込みの維持または能力判定が必要）。
4. PRoot 向けフラグ・補完チェック無効化・ロケール固定などは、WSL での必要性を確認せずに流用しない。
5. `zsh-completions` の二重登録（fpath と plugins の両方）を引き継がず、設計で整理する。
6. `cd` の置換や端末固有の安全策・補助ツール起動などは、本人の希望を確認せずに追加しない。
7. `gg` の全 stage・自動 commit/push を勝手に有効化しない。操作前確認とキャンセル時の状態を明示する。
8. 「コミット済みだが未 push」だけの状態で `gg push` が何もしない参照実装の癖は、再設計するなら修正候補とする。
9. `gg` の設定ファイルは一時ファイル経由の置換で書き換えられるため、ファイル単位のシンボリックリンクと相性が悪い。ディレクトリ単位の扱い・書き込み方法・ローカル専用化を検討する。
10. 特殊なファイル名・ブランチ名、未追跡ファイルの差分、upstream 無し、初回コミット前、失敗時終了コードなどをテストしてから採用する。
11. ホーム全体や履歴ファイルまで Git 管理する参照先の構成は踏襲しない。必要な設定だけを選ぶ。
12. コードを転載・再配布する場合は、権利者の許可・ライセンスを先に確認する（構造・機能を参考に独自実装する方法もある）。

## 設計を再開するときの順序

1. 参照先と現在の設定を比較し、「採用する構造 / 維持する設定 / 変える挙動」を短く整理する。
2. リポジトリ内の配置（例: `zsh/`）と、ホームからのリンク対応表を確定する。
3. `gg` の操作仕様（全 stage の扱い、自動 push、pull 方針など）を確定する。
4. 公開範囲・端末差分・秘密情報の分離を決める。
5. 合意後、まず一時 HOME で配置とリンクの双方向反映（編集→差分 / pull→反映）を試験する。
6. ユーザー実環境はバックアップを取り、段階的に移行する。

質問を一度に繰り返すより、参照先を踏まえた具体案を示して決める進め方が合意されています（質問方法の規約は `AGENTS.md §7.4`）。
