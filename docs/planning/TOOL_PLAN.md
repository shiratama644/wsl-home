## 2. 目的 (Why)

設定の実体をリポジトリに 1 つ置き、ホーム側の編集がそのまま Git 差分になる持ち方を、段階的に安全へ倒しながら実現する。各段階で「実際に使えるもの」が手元に残る順序（中核 → パイロット移行 → 拡張 → 引っ越し → 暗号化 → TUI）とし、使い勝手と安全性を早い段階で確かめてから複雑な機能に進む。既存の WSL 環境と Starship の見た目は壊さない。

## 3. 変更範囲 (Scope)

変更対象:
- `tool/`（dotctl 本体。Bun + TypeScript。新規）
- `dotctl.toml`（対応表。段階ごとに対象を広げる）
- 配置対象の実体（`zsh/`・`config/`・`git/`・`etc/`・`secrets/`。段階ごとに追加）
- `docs/arch/tool.md`（仕様の追随更新）、`docs/arch/milestones.md`、`docs/task-list.md`、必要に応じて `docs/ops/`（引っ越し・identity 手順）
- `AGENTS.md` §6.1 と `Makefile` の `PROJECT_CHECKS`（Bun 検証コマンドの登録。TOOL-1 で実施）

変更しない (境界外):
- ユーザー実環境（`/home/ubuntu`）のファイル。AI の変更は本リポジトリへのコミットまで（実適用は本人の承認・実行）
- Starship の見た目、既存の mise / uv / Go / Rust / Git / Docker 構成、システム Python
- `.agent/` と `AGENTS.md` の骨格（規約。§6 のプロジェクト固有部分の追随更新は除く）
- 参照リポジトリ UbuntuHome のコードの転載（構造・機能の参考まで。転載する場合はライセンス・許可を先に確認）

## 4. 禁止事項

- 秘密情報（鍵、トークン、`.env`、実メールアドレス等）をリポジトリに置かない（暗号文の扱いは tool.md §10・§13 の制約に従う）
- 設計にない破壊的挙動（既存ファイルの上書き・削除、`sudo`、ホーム外への書き込み）を dotctl に入れない
- テストで実ホームに触らない（一時ディレクトリのみ）
- テストを通すためだけに期待値を実装へ合わせない。仕様と合わなければ仕様側の判断を仰ぐ
- 不明点は推測で埋めず、§7 の停止条件に従って質問する

## 7. 停止条件

次の場合は作業を停止し、変更せず報告する:
- 仕様書 (計画書・AGENTS.md・skills) 同士に矛盾がある
- task-list.md 記載の変更範囲を超える変更が必要
- 破壊的変更 (既存データ・公開 API 互換性) が必要
- ユーザー判断が必要な設計論点に到達した（例: 暗号文の公開可否、移行対象の追加、gg の挙動変更）
- 開始時点で作業ツリーに未確認の変更がある
- ユーザー実環境の操作（配置・インストール・ファイル移動）が必要になった（手順の提示に留める）
- SPIKE-1 で AI 作業環境の Bun 実行が不可だった場合の中核実装開始（代替の検証手順を決めてから）

## 11. リスク・Gotchas

- **リンクの通常ファイル化**: エディタやインストーラがリンク先を通常ファイルに置き換えることがある。`check` で検出し、差分の回収 → バックアップ → リンク再作成の順で戻す。ロールバックは `~/.config-backups/dotctl-<日時>/` の控えと Git の履歴から行う
- **Bun の実行可否**: AI 作業環境で Bun が動かない場合は中核実装の検証手段が崩れる。SPIKE-1 を先に実証し、不可なら代替（CI で検証する等）を §6.1 に記録する
- **生成物の編集取り違え**: ホーム側の生成物を編集しても差分にならない。ドリフト検出と `edit` 導線で防ぐ
- **identity 紛失**: 暗号文が復号不能になる。作成直後に安全な控えの手順を運用文書で案内する
- **現行 `.zshrc` の確定**: プラグイン導入後の最終形が未取得。MIG-1 の zsh 段では現行ファイルの提供を受け、古い内容で上書きしない
- **ロールバック（全体）**: dotctl 導入前の状態へ戻す場合は、リンクを消して `~/.config-backups/` の控えを戻す。リポジトリ側は Git の履歴で戻せる
